# Отладочный разбор теста `findByIdReturnsEntityForExistingKey`

Разбор отвечает на вопрос: **что происходит внутри jOOQ шаг за шагом**, когда выполняется

```java
@Test
void findByIdReturnsEntityForExistingKey() {
    AuthorRecord created = authors.create("Find Me", "Португалия");  // строка 31 теста

    AuthorRecord found = authors.findById(created.getId());          // строка 33 теста

    assertNotNull(found);                                            // строка 35+
    assertEquals(created.getId(), found.getId());
    assertEquals("Find Me", found.getName());
    assertEquals("Португалия", found.getCountry());
}
```

Разбор основан на **реальном прогоне** этого одного теста двумя способами:

1. **Под отладчиком (jdb)** — с точками останова в `AuthorRepository.create/findById`,
   `SelectImpl.where`, `AbstractResultQuery.fetch` (стеки и локальные переменные ниже);
2. **Со включённым логом jOOQ** (`LoggerListener`, уровень FINE) — в лог попал каждый SQL
   вместе с bind-значениями и результатом выборки.

Как повторить отладочную сессию — в конце документа.

---

## Шаг 0. `@BeforeEach` — поднятие изолированного стенда

```java
db = Database.open("test_" + UUID.randomUUID());   // AbstractRepositoryTest
SchemaSeeder.init(db.dsl());
authors = new AuthorRepository(db.dsl());
books  = new BookRepository(db.dsl());
```

Что происходит:

| Действие | Класс / метод | Суть |
|---|---|---|
| Пул соединений | `JdbcConnectionPool.create("jdbc:h2:mem:test_<uuid>;DB_CLOSE_DELAY=-1", ...)` | У каждого теста **своя** in-memory база — данные не пересекаются |
| Конфигурация | `new DefaultConfiguration().set(SQLDialect.H2).set(new DataSourceConnectionProvider(pool)).set(new Settings())` | Собирается «хаб»: диалект, источник соединений, настройки. Именно `Configuration` раздаёт всё это механизмам jOOQ |
| DDL | `SchemaSeeder.init` → `dsl.createTableIfNotExists(AUTHOR)...` | Даже DDL — обычные `QueryPart`-ы; в лог попадает: `create table if not exists "AUTHOR" ("ID" bigint not null generated by default as identity, "NAME" varchar(120) not null, "COUNTRY" varchar(60), primary key ("ID"))` |
| Сиды | `insertAuthor(...)` × 4, `insertBook(...)` × 12 | В логе — 4 insert’а с `returning`-хвостом и 12 прямых insert’ов |

После `@BeforeEach` в базе: 4 автора, 12 книг. Тестовый автор получит **ID = 5**.

## Шаг 1. `authors.create("Find Me", "Португалия")` — подготовка данных

```java
// AuthorRepository.java:24
public AuthorRecord create(String name, String country) {
    AuthorRecord r = dsl.newRecord(AUTHOR);   // строка 25 — здесь сработал брейкпоинт
    r.setName(name);
    r.setCountry(country);
    r.store();
    return r;
}
```

* `dsl.newRecord(AUTHOR)` — jOOQ спрашивает у таблицы её тип записи
  (`Author.getRecordType()` → `AuthorRecord.class`) и создаёт сущность конструктором
  без аргументов. `AuthorRecord` наследует `UpdatableRecordImpl`, поэтому «умеет»
  `store()/update()/delete()/refresh()`.
* `r.store()` — у **новой** записи (первичный ключ не задан) это INSERT. Внутрь
  смотрит `UpdatableRecordImpl.store()` (`UpdatableRecordImpl.java:146 → 154 → store0:198`):
  чтобы понять, insert это или update, записи нужен первичный ключ таблицы —
  поэтому в `Author` мы объявили `Internal.createUniqueKey(this, this.ID)`.
* SQL рендерится тем же механизмом, что и SELECT, и в логе выглядит необычно —
  это фича H2 «data change delta table», которой jOOQ пользуется для `RETURNING`:

  ```sql
  select "ID" from final table (insert into "AUTHOR" ("NAME", "COUNTRY") values (?, ?)) "AUTHOR"
  -- with bind values: ('Find Me', 'Португалия')
  ```

  то есть вставка исполняется как запрос, из которого читается сгенерированный ключ.
* Сгенерированный **ID = 5** jOOQ записывает обратно в поле записи (`created.getId() == 5`).

Стек на брейкпоинте `create` (верхние фреймы, из jdb):

```
[1] org.example.bookshop.repository.AuthorRepository.create (AuthorRepository.java:25)
[2] org.example.bookshop.repository.AuthorRepositoryTest.findByIdReturnsEntityForExistingKey (AuthorRepositoryTest.java:31)
```

## Шаг 2. `authors.findById(5)` — построение запроса

```java
// AuthorRepository.java:33 — здесь сработал брейкпоинт
public AuthorRecord findById(long id) {
    return dsl.selectFrom(AUTHOR)      // 2а
              .where(AUTHOR.ID.eq(id)) // 2б
              .fetchOne();             // 2в
}
```

Локальные переменные на входе метода (jdb `locals`): `id = 5`.

### 2а. `dsl.selectFrom(AUTHOR)` — рождается фасад

`DefaultDSLContext.selectFrom(...)` (`DefaultDSLContext.java:2057`) — одна строка:

```java
return new SelectImpl(configuration(), null).from(table);
```

* Создаётся **`SelectImpl`** — fluent-фасад. В конструкторе он создаёт свой
  **делегат** `SelectQueryImpl` (реальное хранилище состояния запроса).
* `.from(AUTHOR)` (`SelectImpl.java:338`) добавляет таблицу в делегата
  (`delegate.addFrom(...)`) и возвращает `this` — объект один, меняется только
  объявленный тип (интерфейс-«шаг» `SelectFromStep → SelectWhereStep`).

### 2б. `.where(AUTHOR.ID.eq(5))` — условие как объект

* `AUTHOR.ID.eq(5)` создаёт объект условия. В отладчике на брейкпоинте внутри
  `SelectImpl.where` локальная переменная это подтверждает:

  ```
  conditions = instance of org.jooq.impl.Eq
  ```

  т.е. условие равенства — это маленький `QueryPart` (узел будущего дерева),
  внутри которого поле `AUTHOR.ID` и `Param` со значением `5`.
* `SelectImpl.where(Condition)` (`SelectImpl.java:381`) запоминает, что идёт
  секция WHERE, и вызывает `delegate.addConditions(condition)`
  (`SelectQueryImpl.java:4525`). SQL-строки ещё **нет** — есть только дерево.

### 2в. `.fetchOne()` — исполнение

`SelectImpl` наследует `ResultQueryTrait`, где `fetchOne()` определён так
(`ResultQueryTrait.java:508`):

```java
default R fetchOne() {
    return Tools.fetchOne(fetchLazyNonAutoClosing(), hasLimit1());
}
```

* `fetchLazyNonAutoClosing()` запускает **тот же `AbstractQuery.execute()`**
  (шесть фаз ниже), но курсор не закрывается сразу;
* `Tools.fetchOne(cursor, hasLimit1())` берёт первую строку, убеждается, что
  второй нет (иначе — `TooManyRowsException`), и возвращает `AuthorRecord` либо `null`.

| Фаза | Класс/метод | Что конкретно произошло в этом прогоне |
|---|---|---|
| [1] Контекст | `new DefaultExecuteContext(c, this)` | «Блокнот» прогона; внутри `configuration.derive(...)` — производная конфигурация, чтобы все операции теста делили одно соединение. Параллельно собирается композит `ExecuteListeners` из провайдеров |
| [2] Рендер | `Rendered.rendered(...)` → `DefaultRenderContext.visit(query)` → у каждого узла `accept(ctx)` | Дерево печатает себя. В логе: `select "AUTHOR"."ID", "AUTHOR"."NAME", "AUTHOR"."COUNTRY" from "AUTHOR" where "AUTHOR"."ID" = cast(? as bigint)`. Одновременно собран список параметров: `[5]` |
| [3] Соединение | `connection(ctx)` → `ConnectionProvider.acquire()` | Пул H2 отдаёт `Connection` (обёрнутый в `SettingsEnabledConnection`) |
| [4] Подготовка | `prepare(ctx)` → `connection.prepareStatement(sql)` | Обычный JDBC `PreparedStatement` |
| [5] Bind | `new DefaultBindContext(c, ctx, stmt).visit(params)` | Для параметра `5` вызывается `field.getBinding().set(...)` → `stmt.setLong(1, 5)` |
| [6] Исполнение | `execute(ctx, listener)` → `stmt.execute()` | Приходит `ResultSet` |

Две детали, которые видны в реальном SQL:

* **`cast(? as bigint)`** — jOOQ сам добавил CAST, чтобы тип параметра совпал с типом
  колонки на стороне БД (значение-то у нас `int` в Java-вызове `findById(long id)`).
* Колонки перечислены **квалифицированно** (`"AUTHOR"."ID"`), потому что `selectFrom`
  знает таблицу-источник — квалификатор берётся у каждого поля из его таблицы.

## Шаг 3. `ResultSet` → `AuthorRecord`

После `stmt.execute()` jOOQ создаёт `CursorImpl`, который читает строку результата
в `Record` и — благодаря `Author.getRecordType()` — заворачивает её в **`AuthorRecord`**
(нашу «сущность»). В логе:

```
Executing query          : select "AUTHOR"."ID", "AUTHOR"."NAME", "AUTHOR"."COUNTRY" from "AUTHOR" where "AUTHOR"."ID" = cast(? as bigint)
-> with bind values      : ... where "AUTHOR"."ID" = 5
Fetched result           : +----+-------+----------+
                         : |  ID|NAME   |COUNTRY   |
                         : +----+-------+----------+
                         : |   5|Find Me|Португалия|
Fetched row(s)           : 1
```

`fetchOne()` при **одной** строке возвращает её; если бы строк не было — вернулся бы
`null` (это проверяет соседний тест `findByIdReturnsNullForUnknownKey`).

Соединение возвращается в `ConnectionProvider.release()` — jOOQ делает это в `finally`
гарантированно, ровно один раз.


(`java.util.logging.config.file`, `org.jooq.level=FINE`): встроенный
`LoggerListener` напечатает каждый запрос вместе с bind-значениями.
